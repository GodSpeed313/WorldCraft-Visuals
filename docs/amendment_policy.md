# Amendment Policy — what may be done to locked text

**Status:** POLICY — a standing governing instrument. It rules on the lifecycle of this corpus's own
documents and on nothing else. **It is not locked**; see §5.

**What this file is.** The corpus's answer to a single question: once a document is locked, what may
be done to its text. The answer is nothing, and this file states what replaces amendment.

**What this file is not.** It is not a section or appendix of any contract or ruling, and it
governs no subject matter — no state, no taxonomy, no registry. It authorizes no edit; permission
to edit text is `authorizations.md`'s act and this file grants none. It records no defect; defects
in text go to `corrections.md`, which closes nothing and authorizes nothing. It records no gap;
what a document must gain goes to `open_contract_gaps.md`. It is not a method checklist; how to
sweep is `audit_method.md`'s subject. This file states a standing rule about document lifecycle,
and only that.

**Why this file was created on 2026-08-28.** Contract 001 locked on 2026-08-25, and with it the last
of the corpus's governing documents. GAP-9 recorded that no instrument stated what may be done to a
locked document's text, who may authorize it, or what a signature on the result would attest. The
operator determined on 2026-08-25 that locked text has no amendment route and that supersession is
the only route. This file is where that determination lives. It is filed as its own instrument
rather than inside `authorizations.md` because instruments here are routed by the behavior they
perform, not by subject matter: `authorizations.md` records bounded, one-time grants that close when
their commit lands, whereas this is a standing rule that never closes. `audit_method.md` is the
structural analogy.

## 1. The rule

**Text in a document that carries a LOCKED status is not amended.** No instrument in this corpus
authorizes such an amendment, and no instrument may. There is no bounded exception, no minor-repair
exception, and no exception for a defect the corpus itself has recorded.

The act of marking a document LOCKED is the last edit that document receives.

**What this rule settles about a recorded defect, and what it does not.** Defective locked text is
never edited, and a correction entry against it will never be answered by a change to the text it
describes. That much is not this policy's invention: the corrections register already holds that
such an entry *"records a defect in text that is already signed, and closes nothing"*
(`corrections.md:9`), and that *"the signed text stays as attested"* (`corrections.md:13`). This
rule makes that permanent rather than provisional.

**It does not follow that a recorded defect governs forever.** §3 supplies the remedy: a division
containing one can be superseded, after which it stops governing while its text remains on the page
exactly as attested. The text is unrepairable; what it governs is not. Nothing here holds that a
recorded defect is beyond remedy — only that the remedy is never an edit.

## 2. Scope

**This policy binds every document in this corpus carrying a LOCKED status, whatever their number,
including a set of one and the empty set.** It bound the corpus before any document was locked, when
it was vacuously true, and it will bind an arbitrary number of them later.

**No clause of this policy may name a specific document.** Documents are named in this file only as
evidence — recording what has already happened — never as the subject of a rule. A clause that would
have to be rewritten when a document is added, locked, or superseded is a defective clause.

**Conformance check.** Substitute the set of locked documents with any other set of locked
documents, of any size, including a set of one and including none. If any clause of this policy
changes meaning, becomes inapplicable, or requires rewriting, this policy is violated.

**A document is locked when its own text says so** — a status line declaring it LOCKED, on the
document's own authority, following full sign-off. This policy does not decide when a document
should be locked, who may lock it, or what locking attests. It governs only what follows.

## 3. Supersession

**Supersession is the only route by which locked text stops governing.** A superseding document is
one that states in its own text that it supersedes identified text in another document.

**Supersession operates at the granularity of an addressable division** — a section or subsection —
**not only at whole documents. This is a decision taken here, not a rule the corpus already
carried.** A superseded division stops governing. Every other division of that
document continues to govern, and the document's LOCKED status is unchanged by the supersession of
any part of it. Whole-document supersession is the limiting case in which every division is
superseded at once; it is not the ordinary case, and nothing here requires a superseding document to
replace more than it names.

**The superseded document is not touched.** It is not edited, not annotated, not marked, and not
corrected. It carries no notice that it has been superseded in part, because placing one would be an
amendment to locked text, which §1 forbids.

**A superseding document is subject to this policy in its own right** once it carries a LOCKED
status, and may itself be superseded on the same terms.

**What the precedent establishes, and what it does not.** Ruling 002 supersedes Ruling 001 §7.1 and
nothing else; Ruling 001 remains locked and binding, and its own sign-off records §7.2 through §7.7
as open and owned by it. That is one section-level supersession, and the only governance
supersession in this corpus. It establishes that the route is **available** — the corpus has read a
single prior act that way before, treating one amendment as *"the standing precedent that the route
is available in this corpus when the defect is a local, definitional repair"*
(`contract_001_domain_resolution.md:320`) — but availability on one set of facts is not a general
operating rule, and **how far a single precedent reaches is itself undecided here**: the proposition
that *"precedent applies by shared reason, not by analogical extension"* was considered and recorded
as outside Ruling 002, which settled only that it does not belong there
(`ruling_002_family_taxonomy_integrity.md:636`). The granularity rule above is therefore adopted
here rather than inherited, and it is adopted because the narrower alternative — supersession at
whole documents only — would fail to describe the one case that has actually occurred.

## 4. Discoverability

The precedent in §3 carried a marker inside the superseded document, placed two days before that
document was locked, while it was still editable. **That half of the precedent is not reproducible
and must not be relied on.** Under §1 and §3, no future supersession can annotate what it
supersedes.

The consequence is stated plainly rather than left to be discovered: **a reader of a locked document
cannot learn from that document that one of its divisions has stopped governing.** The information
exists only in the superseding document.

**Therefore a superseding document must identify what it supersedes precisely enough to resolve
without inference** — the document, and the division within it. A statement that one document
supersedes another in general terms, or that leaves a reader to work out which divisions are
affected, does not satisfy this requirement and leaves the supersession unstated.

This policy imposes no obligation on any reader and creates no index. Whether a check for
supersessions belongs on the standing sweep checklist is `audit_method.md`'s decision, under its own
rule that an item earns a slot when a technique has failed in a way that would recur — which has not
yet happened here.

## 5. This instrument's own status

**This policy is not locked, deliberately.** A lifecycle instrument that could not absorb what is
later learned about lifecycles would be the wrong trade. It is a governing document, unlike the gap
register and the method checklist, both of which are freely editable precisely because they rule
nothing; this one rules something and is freely editable anyway. **Its protection is disclosure, not
immutability.**

**How this file is amended, and on what basis.** By direct edit, recorded in place with a dated
note, in the manner the gap register already uses for its own amendments. The basis is not that this
file is unlocked; a document is not editable merely for being unlocked. It is that **nothing attests
this file** — it carries no signature and no sign-off box, so an edit to it disturbs no attestation.
That is the ground the corpus already gives for when permission is needed: the authorizations file
exists to protect attested text, its first entry resting on the target being unsigned so that *"no
attestation is disturbed by an edit made before signature"* (`authorizations.md:38-39`), and the
corrections register holding that *"the signed text stays as attested"* (`corrections.md:13`).

**Stated for this file only, because no document states a general rule.** Standing instruments here
have been edited in place with no authorization entry — a checklist appended to, a register amended
inline and dated — but no instrument records a rule permitting it. This section states the rule for
this file. It decides nothing about how any other instrument may be edited and creates no general
licence.

**An amendment to this policy has no retroactive effect.** Changing this text cannot legitimize an
edit that was forbidden when it was made, and cannot convert a past amendment of locked text into an
authorized one.

**If this policy is ever locked, it falls under its own rule** and may from then on be changed only
by supersession. Nothing here anticipates that; the rule applies to itself on the same terms as to
anything else.

## What this file does not do

- It authorizes no edit, to any document, locked or not.
- It ticks no sign-off box and contains no signature.
- It reopens no lock and revisits no signature already given.
- It closes no register entry. Recording a closure is a separate act under that register's rules.
- It repairs no correction entry and decides nothing about any defect already recorded.
- It decides nothing about when a document should be locked, or by whom.
